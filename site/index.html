一个像素风的宝石切割放置游戏：敲开原石，定下宝石底部的角度，磨出刻面。切好的宝石会发光，光就是游戏里的钱。

  • 2 天从第一个原型到在 itch.io 公开发布，共 26 次提交
  • 300+玩家玩过，中英双语，按浏览器语言自动切换
  • 0 后端整个游戏是一个 HTML 文件，进度存在浏览器里

灵感来自一期讲钻石为什么会闪的视频。我想把“光进去就出不来”变成可以亲手试的东西：定角时，游戏在宝石截面上追踪每一条光线，按真实折射率和菲涅尔方程算出能留住多少光。钻石的临界角是 24.4°，萤石只有大约 2° 的窗口，这些差别都直接变成了手感。

关键取舍 · 4 条

  2. 11.04itch.io 的玩家多数读英文，所以把所有文字抽到一张对照表里，中英双语，按浏览器语言自动选择，也可以手动切换。
  3. 11.04视觉整体重做成“晶体学图版”风格，但宝石保留像素风：3D 像素宝石和它下面的彩色光斑，是这个游戏最让人记住的东西。

工作方法

我怎样和 AI 一起做工程

用 Agent 提速，但每一步都留下可以检查的证据：任务能判断对错，运行能复现，边界由环境保证，验证分层报告。

  1. 先写能判断对错的任务，再交给 Agent

    目标、已有上下文、硬约束、允许修改的范围和验收证据，分开写清楚。

  2. 冻结起点，保留失败

    同一个 commit、Prompt、模型和权限。先记录原始运行结果，再做人工修正。

  3. 让环境落实边界

    Prompt 里写了禁止，不等于环境真的禁止。能力边界要靠工具层和权限控制，完成与否由独立的验证来判断。

  4. 分层验证，分层报告

    单元测试、真实模型、浏览器、实机、云端、用户反馈各说各的。本地成功不等于已经部署。

  5. 让每个生成结果都能追溯来源

    保留字段编号、版本、原文和哈希。恢复时不悄悄重新生成历史结果。

另外 5 条

  1. 用领域模型消除歧义

    常见做法不等于必要条件。例外太多时，重新划分类别，而不是继续加规则。

  2. 证明非法输入会被拒绝

    正向示例能编译还不够。TDD 的“红”必须是目标断言失败，环境报错不算。

  3. 任务结果和实验有效性分开判断

    功能通过了，归因仍可能无效。一个分数代替不了这两个判断。

  4. 先判断值不值得封装，再建 Skill

    同样的输入、判断和验收反复出现，才值得封装。已有的 Skill 能扩展，就不再新建一个。

  5. 多个 Skill 协作时，先定状态归谁

    上游负责生命周期，下游只返回判断结果。交接只传必要信息，不自动扩大写入权限。

Method

How I build with AI

Agents for speed, but every step leaves evidence I can check: tasks that can be judged, runs that can be reproduced, limits enforced by the environment, and verification reported in layers.

  1. Write a task that can be judged right or wrong, then hand it to the agent

    Goal, existing context, hard constraints, what may be changed and the evidence for acceptance, each written out on its own.

  2. Freeze the start, keep the failures

    Same commit, prompt, model and permissions. Record the raw run first, then make manual fixes.

  3. Let the environment enforce the limits

    Forbidding something in the prompt doesn't mean the environment forbids it. Limits belong in the tool layer and permissions, and independent checks decide what is done.

  4. Verify in layers, report in layers

    Unit tests, real models, browser, device, cloud and user feedback each report on their own. Working locally is not deployed.

  5. Make every generated result traceable

    Keep field IDs, versions, source text and hashes. A restore never quietly regenerates past results.

5 more

  1. Use a domain model to remove ambiguity

    Common practice is not a requirement. When exceptions pile up, redraw the categories instead of adding rules.

  2. Prove that bad input gets rejected

    A passing happy-path example is not enough. In TDD, “red” must be the target assertion failing. An environment error doesn't count.

  3. Judge task outcome and experiment validity separately

    The feature can pass while the attribution is still invalid. One score can't stand in for both.

  4. Decide if it's worth packaging before building a skill

    Only the same inputs, calls and checks coming up again and again justify a skill. If an existing skill can be extended, I don't build a new one.

  5. When skills work together, decide who owns state first

    Upstream owns the lifecycle. Downstream only returns its call. The handoff carries only what is needed and never widens write access on its own.

La première transforme les contenus sauvegardés en fiches d'usage et gère leur état. La seconde décide seulement si une preuve doit changer un projet : adopter, expérience minimale, reporter ou refuser.

  • Au départ, leurs rôles se chevauchaient. J'ai redessiné la frontière : l'état appartient à l'amont seul, l'aval ne renvoie que son jugement, et le relais passe par l'accord de l'utilisateur.
  • Le jugement de valeur revient à l'Agent ; les scripts se limitent au scan, au hash, à l'index et aux contrôles de structure. Test réel sur 5 sources : tous les SHA-256 inchangés.

Méthode

Comment je fais de l'ingénierie avec l'IA

Les agents pour la vitesse, mais chaque étape laisse des preuves vérifiables : des tâches qu'on peut juger, des runs reproductibles, des limites imposées par l'environnement, une validation rapportée par niveaux.

  1. Écrire une tâche vérifiable avant de la confier à l'Agent

    Objectif, contexte existant, contraintes fortes, périmètre modifiable et preuves de validation : chacun écrit à part, clairement.

  2. Figer le point de départ, garder les échecs

    Même commit, même Prompt, même modèle, mêmes droits. On consigne d'abord le résultat brut, puis on corrige à la main.

  3. Laisser l'environnement faire respecter les limites

    Un interdit écrit dans le Prompt n'est pas un interdit dans l'environnement. Les limites se contrôlent au niveau des outils et des droits, et la fin d'une tâche se juge par une vérification indépendante.

  4. Valider par niveaux, rendre compte par niveaux

    Tests unitaires, modèle réel, navigateur, appareil, cloud, retours utilisateurs : chacun son verdict. Réussir en local ne veut pas dire être déployé.

  5. Rendre chaque résultat généré traçable

    Conserver numéros de champs, versions, textes sources et hash. À la reprise, ne pas régénérer en silence les résultats passés.

5 principes de plus

  1. Lever l'ambiguïté par le modèle du domaine

    Une pratique courante n'est pas une condition nécessaire. Quand les exceptions s'accumulent, on redécoupe les catégories au lieu d'empiler des règles.

  2. Prouver que les entrées invalides sont refusées

    Que les exemples valides compilent ne suffit pas. En TDD, le « rouge » doit venir de l'assertion visée, pas d'une erreur d'environnement.

  3. Juger à part le résultat et la validité de l'expérience

    Une fonctionnalité peut passer et l'attribution rester invalide. Un seul score ne remplace pas ces deux jugements.

  4. Juger si ça vaut une Skill avant d'en créer une

    Il faut que les mêmes entrées, jugements et validations reviennent souvent. Si une Skill existante peut s'étendre, on n'en crée pas une nouvelle.

  5. Avec plusieurs Skills, décider d'abord à qui appartient l'état

    L'amont gère le cycle de vie, l'aval ne renvoie que son jugement. Le relais ne transmet que le nécessaire et n'élargit pas les droits d'écriture.
